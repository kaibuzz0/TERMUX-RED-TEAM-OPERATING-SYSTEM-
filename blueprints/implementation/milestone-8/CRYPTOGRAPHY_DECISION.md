# HIVE OS Vault Cryptography Decision

**Milestone 8**

## Decision

Use the Python `cryptography` library, version `>=41.0.0`, already declared in `requirements.txt`.

## Rationale

| Library | Available in CI | Available locally | Termux packaging | Notes |
|---------|---------------|-------------------|------------------|-------|
| `cryptography` | yes (requirements.txt) | yes (48.0.1) | generally available via pip; may require `pkg install rust` for source builds | mature, well-audited |
| `argon2-cffi` | not declared | no | available via pip | preferred KDF but adds dependency |
| `bcrypt` | declared | no | available | unsuitable for encryption keys |
| `PyNaCl` | declared | no | available via pip | libsodium binding; good but currently not installed |
| `hashlib.scrypt` | stdlib | yes | stdlib | available, but lacks modern KDF framing |

`cryptography` is the only mature cryptographic library already installed in the local environment and declared in project dependencies. It supports AES-256-GCM and HKDF, and provides a Fernet convenience class, but we will use the lower-level AEAD API for explicit control over salt/nonce/versioning.

## Selected algorithms

- **Authenticated encryption**: AES-256-GCM via `cryptography.hazmat.primitives.ciphers.aead.AESGCM`
- **Password KDF**: scrypt via `hashlib.scrypt`, with a unique random 128-bit salt per vault file
- **Key-separation KDF**: HKDF-SHA256 with domain-specific info labels
- **Nonce**: 96-bit random nonce per encryption operation, generated by `os.urandom`

## Key hierarchy

```
master_material = scrypt(password, salt, scrypt_params)
encryption_key  = HKDF-SHA256(master_material, info="hive-vault-encryption-v1")
```

- `scrypt` provides memory-hard password derivation.
- `HKDF` domain-separates the AES key from the raw scrypt output and from any future subkeys.
- Future subkeys will use distinct info labels such as `hive-vault-metadata-v1`, `hive-vault-backup-v1`.
- The raw scrypt output is never stored or used directly as a cipher key.

## Authenticated associated data

The AES-GCM AAD binds the ciphertext to the envelope's `schema_version`, `kdf` name, and `cipher` name, preventing algorithm downgrade or field swap attacks.
- **Work-factor parameters** (provisional until Termux benchmarked):
  - **Test profile**: N=2^14, r=8, p=1 (fast tests)
  - **Production profile**: N=2^20, r=8, p=1 (provisional — **requires Android measurement**)

## Versioning

Each vault file carries:

```json
{
  "schema_version": 1,
  "kdf": {"name": "scrypt", "salt": "base64", "parameters": {"n": ..., "r": ..., "p": ...}},
  "cipher": {"name": "AES-256-GCM", "nonce": "base64"},
  "metadata": {"vault_id": "...", "created_at": "...", "updated_at": "..."},
  "ciphertext": "base64",
  "authentication": "base64"
}
```

Unknown `schema_version`, cipher name, or KDF name causes a fail-closed error.

## Limitations

- This is **application-level encrypted credential storage**, not hardware-backed or kernel-isolated.
- It does not protect against an attacker who can execute arbitrary code under the same Termux UID while the vault is unlocked.
- It does not replace Android device encryption or lock-screen security.
- Memory erasure is best-effort only; Python garbage collection and string interning may retain secret material.
